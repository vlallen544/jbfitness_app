# Free hosted demo

This is the deployment preparation for the connected demo, not a claim that services are already live. The current published APK is still an offline preview. No paid resources, live payments or AI calls are enabled by this configuration.

## Services

| Component | Free service | Current scope |
| --- | --- | --- |
| NestJS API | Render Free web service | Authentication and existing customer/staff endpoints |
| Next.js dashboard | Render Free web service | Server-side staff sessions and operations |
| PostgreSQL | Supabase Free | Existing SQL migrations; backend-only access |
| Media | Supabase Free Storage, next integration | Exercise video storage adapter still required |
| Mobile | Flutter APK | Build the connected entry point after hosting is verified |
| AI | Disabled initially | Choose a provider with available free quota, or explicitly labelled sample responses; existing OpenAI adapters are not a free service |
| Payments, calls, push, store | Later steps | Checkout/video providers, notifications and store fulfilment are not implemented by hosting |

Two Render services let the API and dashboard deploy independently. Render's 750 free running hours per workspace are **shared**, not 750 per service. Both sleep after 15 minutes without inbound traffic and can take time to wake. Do not add keep-alive jobs. Open the API and dashboard before the presentation; existing request timeouts may require a retry during cold starts. If both were kept running all month, the shared allowance would be insufficient.

Supabase Free currently includes a 500 MB database and 1 GB file storage, and can pause inactive projects. Check/unpause it before presenting. Render Free Postgres expires after 30 days, so it is deliberately absent from `render.yaml`. Free limits and availability can change.

## 1. Create the database

1. Create a Supabase **Free** organization/project dedicated to the demo, choosing a nearby region where available. Save the database password privately.
2. Disable the **Data API** for this backend-only project before migrating. Our application uses PostgreSQL connections, not Supabase Auth or client database APIs. Do not expose these customer tables through REST/GraphQL. Use a separate project if another app needs the Data API.
3. Click **Connect → Session pooler** and copy the PostgreSQL connection string. Use session mode, normally port 5432. The migration runner uses session advisory locks, so transaction mode on port 6543 is unsuitable.
4. Replace the password placeholder with the URL-encoded database password. Require TLS certificate verification with `sslmode=verify-full`. If the provider certificate needs a CA file, obtain the database CA from Supabase, add it as a Render secret file and configure `sslrootcert=/etc/secrets/<certificate-filename>` in the URL. Do not disable certificate verification.
5. Keep the URL in Render's private environment settings. Do not paste it into Git, screenshots, dashboard public variables or mobile build arguments.

Example shape, **not usable credentials**:

```text
postgresql://postgres.PROJECT_REF:ENCODED_PASSWORD@POOLER_HOST:5432/postgres?sslmode=verify-full
```

## 2. Deploy the API

The root `render.yaml` is a Blueprint for both free services. Commit/push it, then connect the repository in Render → **New → Blueprint**, or create the API first manually with these exact settings. Keep the repository root as the working directory because this is an npm workspace.

| Setting | Value |
| --- | --- |
| Repository | `vlallen544/jbfitness_app`, branch `main` |
| Runtime / region / plan | Node / Singapore / **Free** |
| Build command | `npm ci --include=dev && npm run build --workspace @jbfitness/api` |
| Start command | `npm run db:migrate --workspace @jbfitness/api && npm start --workspace @jbfitness/api` |
| Health check | `/api/v1/health` |
| Environment | As listed in `render.yaml`; private `DATABASE_URL` supplied by you |

Use the actual assigned HTTPS service URLs; names can vary. Set `CORS_ORIGINS` to the dashboard's exact HTTPS origin with no trailing slash. During sequential setup it can temporarily be `https://example.invalid` until the dashboard exists. Native Android/iOS requests do not use browser CORS.

The signing key is generated by the Blueprint; for a manual deployment generate a random private value of at least 32 characters. Keep all feature flags in the Blueprint disabled. The API must bind `HOST=0.0.0.0` and use Render's supplied `PORT`. Do not set a fixed port.

Migrations run at startup because free services do not offer a pre-deploy command. They are versioned and locked; failed migrations prevent the app from starting. `tsx` is required by the migration runner, hence `--include=dev`. Future production migrations need their own rollout/backup procedure.

## 3. Deploy the dashboard

Use the second Blueprint service, or another **Free** Node web service with the same repository root:

```text
Build: npm ci --include=dev && npm run build --workspace @jbfitness/admin
Start: node node_modules/next/dist/bin/next start apps/admin --hostname 0.0.0.0 --port "$PORT"
```

Set `NODE_VERSION=24`, `NODE_ENV=production`, `API_URL=https://<actual-api-host>/api/v1`, and `DASHBOARD_ORIGIN=https://<actual-dashboard-host>`. The API URL is server-only; do not introduce `NEXT_PUBLIC_` credentials. Update API `CORS_ORIGINS` with the actual dashboard origin and redeploy. Blueprint prompts cannot automatically append `/api/v1` to a discovered service URL, so enter the complete value manually.

The dashboard requires a Node server for its staff cookie sessions and operations proxy. Uploading its files as a static website does not supply that behavior.

## 4. Provision staff and check the connection

Register a dedicated test staff account using the existing API/mobile registration flow, then promote it with the existing provisioning CLI. Render Free does not offer a service shell, so run the CLI locally against this demo database using a private ignored environment file. Do not overwrite the local development `.env`.

From `apps/api`, with a private `.env.hosted-demo` containing **only** the demo database connection (and any required local CA path):

```bash
node --env-file=.env.hosted-demo --import tsx scripts/staff-role.ts --email YOUR_STAFF_EMAIL --role admin
```

This revokes the account's existing sessions. Sign in again through the dashboard. Do not promote a customer account with memberships. Provision a separate trainer account in the same way with `--role trainer` when needed.

Verify, in order:

1. API `GET /api/v1/health` and `GET /api/v1/plans` return JSON successfully.
2. Dashboard opens over HTTPS and staff sign-in works.
3. Register a separate sample customer; save a profile; confirm the customer appears in operations.
4. Restart the API and confirm the account/profile persist in Supabase.

Existing development membership/workout fixtures are not automatically enabled on the production-mode demo. Admin membership activation and suitable hosted sample workouts need their own implementation before demonstrating paid screens with live accounts.

## 5. Build the connected mobile app

After the server works, build the real entry point, **not** `lib/main_preview.dart`:

```bash
bash scripts/mobile.sh build apk --debug --target lib/main.dart --dart-define=API_BASE_URL=https://ACTUAL_API_HOST/api/v1
```

Output: `apps/mobile/build/app/outputs/flutter-apk/app-debug.apk`. This development-signed APK is for testing, not store release. Installing over the offline preview may retain its sample token; sign out/clear app data before testing real registration. Do not upload it under the offline preview release name. Physical-device checks remain required. iOS signing/building requires macOS/Xcode and a separate distribution setup.

## 6. Media and AI follow-up

Progress photos currently persist as processed JPEG bytes in PostgreSQL, so they survive API redeployment but consume the small database quota. Use a few test photos. Exercise videos currently use a private local directory, which is ephemeral on Render Free; attach a private object-storage adapter before promising persistent video playback. A Supabase account alone does not connect storage to the app.

Next: integrate private buckets, preserve membership/ownership checks and short-lived playback access, then migrate progress-photo storage. Do not make customer photos public to simplify the demo.

Current AI adapters require separately configured OpenAI billing/keys. Free hosting does not include free AI credits. Keep AI unavailable until a compatible provider is configured, or show clearly labelled sample outputs in the offline preview. Do not silently present sample outputs as live AI. Real payments remain disabled; use sandbox integration when implemented.

## Troubleshooting startup migrations

`.env not found. Continuing without it.` is expected on Render; its environment variables replace that file. Do not upload a local `.env` to GitHub.

The migration runner now reports a safe failure stage and recognized driver code without printing connection strings, passwords or SQL details. After deploying this revision:

| Diagnostic | Check |
| --- | --- |
| `DATABASE_URL is missing` | Add the variable to the API service, not just the dashboard |
| `ENOTFOUND` | Copy the exact PostgreSQL hostname from Supabase Connect |
| `ENETUNREACH` | Use the IPv4-compatible Session pooler instead of a direct IPv6 endpoint |
| `28P01` | Database password, URL encoding and `postgres.PROJECT_REF` pooler username |
| Certificate errors | TLS provider CA secret file and `sslrootcert` path; do not disable verification |
| `ECONNREFUSED` / timeout | Correct port 5432, active project and network restrictions |
| Failure during a named SQL migration | Investigate that migration and database state; do not drop/reset hosted tables |

An HTTPS Supabase project URL or an API key is not a PostgreSQL connection string. The previous generic message did not identify the cause; these checks are possibilities, not a confirmed diagnosis of an individual failed deployment.

## Scale later

Upgrade API/dashboard compute when cold starts, shared hours or memory constrain the demo; upgrade database/storage as usage grows. Database and media data should remain on managed storage. Add backups, monitoring, recovery, rate-limit persistence and device verification before a real customer pilot.
